# Decisions made while building

Choices the implementation plan left open, or small departures from it, with the reason. Newest last.

## Slice 1

**OPFS SQLite spike: works on desktop Chrome.** `@sqlite.org/sqlite-wasm` 3.53 with the SAH-pool VFS in a dedicated worker opens without cross-origin isolation headers, and data survives a full browser restart with the network off. This is checked by `apps/web/e2e/storage.spec.ts` on every test run. Android Chrome still has to be confirmed by hand (README, "Testing on the Android phone").

**Second tab: "open in another tab", not proxying.** The plan allowed either. A Web Lock held for the life of the page elects the owner; another tab shows a message and takes over automatically when the owner closes. Proxying through the owner tab was more machinery for a single-user app.

**All of core runs inside the worker.** The page calls it by message (`apps/web/src/db`). Core's storage seam is `SqlDriver` (one method, `exec`), with drizzle's `sqlite-proxy` on top, so browser, server and CLI share every query.

**Node SQLite driver is `node:sqlite`, in its own package.** Node 24's built-in driver avoids a native dependency in the server image. It lives in `packages/storage-node` (not in the plan's layout) because core must not import Node APIs, and both core's tests and the server need it.

**Migrations are hand-written SQL in `packages/core/src/migrations.ts`.** They must run in the browser, where drizzle-kit's file-based migrator cannot. The drizzle schema in `schema.ts` remains the one definition used for queries.

**UI primitives are hand-written in the shadcn/ui style** (`apps/web/src/components/ui.tsx`: same token scheme, `cva` variants, Tailwind) rather than generated by the shadcn CLI. Dialogs use the native `<dialog>` element. Generated components can replace them one at a time later.

**The field editor is a plain `contentEditable`,** not a schema-based editor such as Tiptap. Imported Anki fields contain arbitrary HTML that a schema-based editor would rewrite or drop.

**Cards render in a sandboxed iframe without `allow-scripts`.** This is how "no JavaScript in templates" is enforced, and it keeps a note type's CSS away from the app. HTML loaded into the field editor (which is in the page itself) is sanitised first.

**Undo marks the review-log row deleted.** The plan calls the review log insert-only. A row's content is never changed; undo sets `deleted_at`, which only ever goes from empty to set, so it cannot conflict in sync.

**Limits.** New and review limits count what was studied today in a deck's whole subtree, and every ancestor's remaining allowance caps a deck, whether you study the child or the parent. Learning cards are never limited. Learning cards due within 20 minutes are shown early when nothing else is left.

**Review order** is learning cards that are due, then reviews (earliest due first), then new cards (oldest first).

**Built-in note types have fixed ids,** so two devices that seed them while offline produce identical rows.

**TypeScript is pinned to 5.9** because typescript-eslint does not yet accept TypeScript 7.
